# Architecture du hub

## Application

Le [Dockerfile](../Dockerfile) construit React puis publie ASP.NET Core 10 dans une image Linux unique. [Program.cs](../apps/api/Program.cs) configure les Minimal APIs, l’authentification, l’injection de dépendances et les statiques React. Les services reçoivent leurs paramètres avec `IOptions<T>`. EF Core 10 et Npgsql accèdent à PostgreSQL avec les [mappings explicites](../apps/api/Data/AppDbContext.cs) des [entités](../apps/api/Data/Entities.cs).

[CodeInsights.slnx](../CodeInsights.slnx) réunit l’API et ses checks ; [Directory.Build.props](../Directory.Build.props) centralise framework, nullable et versions des packages. Les extensions [VS Code](vscode-extension.md) et [Visual Studio](visualstudio-extension.md) consomment la même API en lecture via `apps/core` ; Visual Studio n'entre pas dans [CodeInsights.slnx](../CodeInsights.slnx) (TFM `net8.0-windows` et SDK VSIX, build Windows à part). Les routes sont regroupées par domaine dans `apps/api/Endpoints`. Les appels HTTP externes passent par `IHttpClientFactory`. Les exports sont produits en CSV sans dépendance de rendu documentaire.

Deux flux d'ingestion sont supportés. Le runner transmet mesures et findings à `POST /api/v1/analyses`. Le client de publication transmet manifeste et originaux à `/api/v1/ingestions` : Blob Storage conserve les fichiers, PostgreSQL conserve reçus, révisions et jobs, puis le worker normalise les rapports et calcule le gate du profil. Les formats de qualité natifs sont SARIF Roslyn, Cobertura/LCOV, jscpd JSON, cloc JSON, Lizard XML, TRX et JUnit ; les rapports sécurité et qualité d'un build sont envoyés dans une seule ingestion. Les effets ADO et notifications sont des jobs distincts, créés dans la transaction du résultat.

Le contrat courant de l'extension `0.5.0` expose `UpCoopSecurityScan@2` comme producteur
sans secret et `UpCoopPublishReports@1` comme publicateur unique. Les
templates AzurePipelines `v3.1.0` fournissent les wrappers .NET, React, Flutter et
Terraform. Seul le publicateur résout l'URL et le jeton CodeInsights depuis la
service connection `CodeInsights-Coop` ; les commandes de build/test/lint ne sont
pas relancées et aucun secret de restore n'entre dans les conteneurs de scanners.
Pour `upcoop-dotnet/2`, la tâche apporte elle-même le ruleset Semgrep
`upcoop-dotnet-mqr/v1`; le dépôt consommateur ne porte aucun fichier
`.codeinsights`.

## Organisation du frontend

Le SPA conserve React, TypeScript, Vite, les contrôles HTML natifs et le CSS partagé. [styles.css](../apps/web/src/styles.css) reste l'agrégateur d'un bundle unique et importe, dans l'ordre, `theme.css`, `shell.css`, `controls.css`, `workspaces-base.css`, `administration.css`, `shared-details.css` et `rules-quality-gates.css`. Les feuilles restent sans `@layer` afin de préserver la cascade historique. [package.json](../apps/web/package.json) et son lockfile déclarent les dépendances ; le [Dockerfile](../Dockerfile) consomme les mêmes versions avec `npm ci`. Cette organisation ne change pas les contrats publics de l'API ni l'identité visuelle.

[App.tsx](../apps/web/src/App.tsx) porte les providers et le cycle de session. [Workspace.tsx](../apps/web/src/workspace/Workspace.tsx) porte la navigation et les sélections communes de projet, branche et analyse ; `workspace/AuthScreens.tsx` rend les écrans de connexion, tandis que `layouts/AppShell.tsx` et `layouts/MainNavigation.tsx` rendent le cadre. L'état métier partageable est sérialisé par `workspace/navigation-state.ts` dans l'URL. `localStorage` conserve la session demandée par l'utilisateur et son choix explicite de thème sous `codeinsights-theme-v1` ; sans ce choix, le navigateur suit le système. Les écrans métier et d'administration restent chargés à la demande avec `React.lazy` sous un état `Suspense` accessible ; le shell, la navigation et le thème restent dans le bundle initial. Si un déploiement a remplacé un chunk encore référencé par un onglet ouvert, l'événement Vite `vite:preloadError` recharge la page ; les réponses HTML portent `Cache-Control: no-cache` afin que ce rechargement récupère le point d'entrée courant. Le panneau avancé des profils n'est monté qu'à sa première ouverture, puis reste monté pour conserver ses brouillons. [useWorkspaceData.ts](../apps/web/src/workspace/useWorkspaceData.ts) regroupe uniquement les lectures communes utiles à la vue active ; les écrans chargent leurs ressources propres. Les types métier sont dans `apps/web/src/types/api.ts`.

Les [features](../apps/web/src/features/) regroupent Projects, Issues, Rules, Quality Gates, Administration et Account. `features/administration/Administration.tsx` rend la navigation des sections sans charger leurs composants avant leur activation. Les contrôles composites partagés restent dans `components/common/`, les primitives dans `components/ui/`, et `config/env.ts` centralise l'URL API et la version affichée. Les imports transversaux depuis `src/` utilisent l'alias `@/` défini par `tsconfig.json` et résolu nativement par Vite/Vitest ; les imports entre voisins restent relatifs. [AGENTS.md](../apps/web/AGENTS.md) décrit l'arborescence cible et les responsabilités locales. Projects intègre les mesures cliquables et l'historique groupé ; Issues concentre les catégories de findings, l'export CSV filtré, les liens source et le suivi. La sous-vue `CodeQualityDetails` reste dans Projects et présente Coverage/Duplications pour l'analyse exacte portée par `analysis_id` et `project_metric`. Elle charge à l'ouverture le source Azure DevOps au commit analysé, affiche au plus 300 lignes de couverture à la fois et libère sa requête lorsque le lecteur est fermé. `MetricGrid` partage la présentation des mesures. Les formulaires et interactions appartiennent à l'écran concerné ; ils ne sont pas transférés dans un store global. L'ancien `ProjectManager`, non monté, et le panneau d'imports non monté ont été supprimés.

[query-client.ts](../apps/web/src/services/query-client.ts) crée un cache par arbre de session : fraîcheur de 30 secondes, aucun retry automatique et aucun refetch au focus ou à la reconnexion réseau. Un changement de session crée un nouvel arbre et annule les anciennes lectures. Les clés portent le contexte métier et les filtres appliqués, jamais le Bearer. Les synthèses, historiques, branches, intégrations et méthodes d'authentification sont activés selon l'écran qui les consomme ; la bibliothèque Quality Gates est l'unique source du gate par défaut. Les mutations mettent à jour ou invalident les ressources concernées ; leurs erreurs restent distinctes d'un succès. [api.ts](../apps/web/src/services/api.ts) centralise l'ajout du Bearer et le rejet des réponses HTTP en échec autour de `fetch`.

Les favoris de projets sont une préférence personnelle persistée côté serveur. Une mutation invalide les synthèses paginées et ciblées, puis repart de la première page. Après fusion de la page courante et du projet sélectionné, le frontend retrie les projets par favori puis par clé afin que Projects, Issues, Rules et Quality Gates partagent le même ordre. Le filtre exclusif reste propre à Projects et n'est donc ajouté à la clé ni à la requête des autres écrans.

Les données serveur restent dans Query ; les sélections, filtres saisis et brouillons restent locaux. Les paramètres utilisent un brouillon partiel, les gates un brouillon lié au gate sélectionné, et les fournisseurs une référence d'initialisation par sélection. Un rafraîchissement du cache ne remplace donc pas une saisie en cours. UsersAccess conserve également localement le brouillon de sa popin et le filtre de projets ; l'ajout seul active la recherche Entra. Les détails des parcours, les bornes de formulaire et les commandes de validation sont dans [Interface](interface.md).

## Identités et données

`new_code_definitions` porte les réglages New Code global, projet et branche ;
`projects.main_branch` fournit la branche principale explicite et chaque
ingestion fige sa résolution dans `new_code_snapshot`. Les anciens champs de
référence des périmètres de code restent lisibles pour les configurations
historiques, mais ne choisissent plus la baseline New Code. Une règle projet
ne peut pas cibler la `main_branch` du projet, mais peut cibler une autre
branche qui s'auto-référencera à sa propre analyse ; voir le piège et le
contournement CI documentés dans [Intégration](integration.md).

Les utilisateurs se connectent avec un compte local ou Entra. À la première arrivée anonyme, le SPA tente une fois dans l'onglet un flux OIDC silencieux `prompt=none`; les erreurs Microsoft qui exigent une interaction reviennent discrètement à l'écran de connexion. Une déconnexion ferme seulement la session CodeInsights et suspend cette tentative dans l'onglet, sans fermer la session Microsoft. Les utilisateurs peuvent créer leurs propres jetons d'accès personnels pour un outillage de poste de travail, en lecture et avec leurs droits exacts. Les producteurs utilisent des tokens CI limités par projets et scopes. L’identité d’accès aux ressources Azure est distincte de ces deux usages. Voir la [matrice des autorisations](security-access.md).

Le schéma contient organisations, projets, grants utilisateur, groupes et grants Entra, périmètres de tokens, transactions OIDC et résultats d’analyse. Les droits Entra sont résolus à partir des appartenances transitives Graph : union des grants directs et de groupe, et rôle le plus fort selon `admin > regular > default`. Un grant interne `all/*`, créé uniquement lorsqu'un administrateur enregistre une affectation sans organisation ni projet, résout toutes les clés de projet ; l'absence totale de grant sur une identité seulement découverte conserve zéro accès implicite. Les appartenances réussies sont mises en cache cinq minutes ; après expiration, une panne Graph applique uniquement les droits directs et `/auth/me` expose `directory_access_status=unavailable`. Un groupe désactivé est ignoré immédiatement et un groupe à appartenance masquée n'est pas assignable sans `Member.Read.Hidden`. Les jetons personnels suivent exactement cette résolution. `user_project_favorites` relie un utilisateur à un projet par une clé primaire composite et des suppressions en cascade. Ce lien ne confère aucun accès : les lectures continuent d'appliquer les grants existants, et un favori masqué par une perte d'accès redevient visible si cet accès est restauré. Les mesures et instantanés historiques restent en JSON texte. L'ingestion ajoute des occurrences de findings, lignes de couverture, composants SBOM et profils versionnés dans des tables dédiées ; les listes utilisent des projections paginées et des synthèses serveur. Les routes de détail qualité lisent `CoverageLine` pour les lignes exécutables et le snapshot `CodeData` borné pour les paires jscpd ; elles n'exposent ni rapport brut, ni finding artificiel. Le fragment source affiché est lu à la demande depuis Azure DevOps, uniquement pour un chemin prouvé par ces données et au SHA exact de l'analyse ; il n'est pas ajouté au modèle de données. Les appels Azure DevOps sortants partagent un jeton Entra court obtenu par l'identité managée système et n'utilisent pas de secret persistant. Les appels Microsoft Graph utilisent séparément le secret Entra existant, un jeton applicatif `.default` et uniquement `https://graph.microsoft.com/v1.0/`, sans SDK Graph. Les migrations EF Core préparent la base avant l’ouverture HTTP. Le bootstrap crée le premier administrateur et les fournisseurs. La connexion est configurée par `ConnectionStrings:CodeInsights` ; les sections `Bootstrap`, `Authentication` et `Analysis` sont liées aux options des services. Les contrats de réponse utilisent `snake_case`.

Les sessions utilisateur peuvent ajouter ou retirer un favori par `PUT` ou `DELETE /api/v1/auth/me/favorite-projects/{project_key}`. Les opérations sont idempotentes ; l'ajout exige un projet autorisé qui possède au moins une analyse, et les tokens CI sont refusés. `/api/v1/insights/summary` expose `is_favorite`, accepte `favorites_only` et utilise un curseur opaque composé du groupe favori et de la clé du projet. L'ordre SQL stable est favori d'abord, puis clé alphabétique, y compris à la frontière entre pages.

La rétention s'exécute via un job de maintenance horaire : le serveur HTTP n'attend pas directement la purge. Le worker durable utilise les verrous PostgreSQL `SKIP LOCKED`, des baux renouvelés, cinq tentatives et une concurrence par défaut de deux. Il calcule aussi les échéances de correction des findings et envoie les résumés de dépassement (jobs `sla` et `sla-notification`, voir [traitement des issues](collaboration.md#délais-de-correction-sla)). Les imports et effets externes survivent aux reprises ; la décoration PR du POST direct passe par le même job durable `pr-decoration`, mais ses notifications restent best-effort en mémoire. Les tests xUnit de `tests/CodeInsights.Tests` couvrent les contrats, la persistance et les autorisations sur des données isolées ([exploitation](exploitation.md#développement-local)).

Le profil immuable `upcoop-dotnet/2` calcule dans le worker les ratings MQR
Overall et New Code avec la formule `sonar-mqr/v1`. Les quatre lettres sont
projetées dans `analysis_records` et leur preuve détaillée reste figée dans le
snapshot JSON. Le catalogue exact des règles, les états de complétude et le gate
sont décrits dans [Ratings MQR](mqr-ratings.md).
L'identité fonctionnelle d'une règle est `(outil, ruleId)`. Les versions d'outil
restent enregistrées comme provenance dans les catalogues, manifestes, rapports
et exports, sans entrer dans les empreintes de configuration ni la compatibilité
New Code. Cette dernière dépend du format et de sa `format_version`.

## Hébergement et évolutions

Le worker évalue la comparaison Git avant les conditions de gate des profils d'ingestion. Les scopes et preuves sont figés dans l'instantané. Les occurrences conservent les métadonnées SARIF de provenance et de localisation ; les liens source ciblent le SHA analysé et aucune copie de code n'est ajoutée. Voir
[nouveau code](new-code.md) et [preuves des rapports](report-evidence.md).

Le modèle initial contient les instantanés de mesures natives, les définitions immuables de périmètres et les correspondances Git. Le worker applique ces périmètres avant les agrégats, contrôle l'empreinte des configurations exécutables, puis évalue la revue selon les décisions figées à la publication. Issues ouvre directement le fichier au SHA analysé sans stocker de sources. Voir [profils et périmètres](profiles.md) et
[revue sécurité](security-review.md).

Le traitement des issues utilise une identité de finding indépendante des occurrences, l'assignation projet/équipe et des décisions de revue conservées après purge des détails. Il est intégré à Issues ; aucun module Portefeuille ou Boards parallèle n'est maintenu. Les tendances de portefeuille reposent sur des snapshots quotidiens calculés par la maintenance (`portfolio_snapshots`, voir [tendances de portefeuille](portfolio.md)) et s'affichent dans All Projects. Les contrats et limites sont dans [traitement des issues](collaboration.md).

## Cycle d’analyse et projection PR

`analysis_records` est l’unique source de vérité. `/api/v1/analyses/start` crée ou retrouve un run `running/pending`; `/complete` persiste une seule fois le snapshot et le verdict `pass`, `fail` ou `unknown`; `/fail` termine en `failed/unknown`. Chaque transition et son job `pr-decoration` sont enregistrés ensemble. Le worker relit toujours l’état courant, donc un ancien job pending ne peut pas restaurer un état obsolète.

Azure DevOps et GitHub sont des projections rejouables. Aucun mapping issue/commentaire ou issue/annotation n’est stocké. Les work items Azure Boards sont l'exception assumée : objets externes modifiés par les équipes, leur identifiant est conservé dans `finding_work_items` pour éviter un doublon et les commenter ([work items](collaboration.md#work-items-azure-boards)). Seul l’identifiant du Check Run GitHub de l’analyse courante est conservé pour terminer ce snapshot immutable. Les sources textuelles strictement nécessaires aux prompts sont séparées des rapports et restent dans le Blob privé.

Le [Terraform](../infra/PLATFORM_SAST.md) définit les ressources Azure. La [pipeline](../.azuredevops/deploy-apps.yml) construit et déploie l’image. Le [Compose](../docker-compose.yml) est destiné au développement local ; son existence ne prouve pas un déploiement Azure.

L'ingestion s'appuie sur le stockage Blob, la queue PostgreSQL, import SARIF/couverture/SBOM et agrégats serveur. `Ingestion:BlobServiceUri` utilise `DefaultAzureCredential` ; `BlobConnectionString` permet notamment le développement Azurite. Le conteneur de rapports est privé et sa création Azure appartient à Terraform. La concurrence est bornée par processus : ajouter une réplique augmente les connexions et la pression sur PostgreSQL. Le parsing conserve un plafond mémoire/entrées, mais ne constitue pas un traitement streaming intégral. Le catalogue des projets et les branches détaillées des synthèses restent des points à mesurer. Le smoke local ne certifie pas la capacité pour plusieurs centaines de projets ; la campagne A/B/C et le pilote Azure restent à réaliser. Voir [intégration](integration.md), [performances](performances.md) et [roadmap](roadmap.md).
