Work items Azure Boards

Un finding peut ouvrir un work item, à la demande ou par des règles, sans doublon et sans que le board ne décide de l'état du finding.

Notes de la slide 1

Lot 2 de la vision cible : les work items Azure Boards. La branche part de develop, qui contient déjà le lot 1 (SLA). Les règles automatiques s'appuient sur les statuts SLA de ce lot.

Contexte

Quatre décisions avant le code

Périmètre

Manuel et règles

Un bouton dans le détail d'une issue, et deux règles automatiques par projet.

Type

Configurable, Bug par défaut

Issue pour un process Basic ; area path et itération facultatifs.

Résolution

Un commentaire

CodeInsights ne ferme jamais le work item.

Destination

Le projet du dépôt

Le lien dépôt Azure Repos désigne le projet Azure DevOps.

La vision cible confie le ticketing à Jira ou GitLab ; dans l'écosystème Up, c'est Azure Boards. Le scan reste la source de vérité : fermer le work item ne change jamais le finding.

CodeInsights · Work items Azure Boards · 4 / 12

Notes de la slide 4

Sans ligne work_item_settings, un projet a les valeurs par défaut : type Bug, pas d'area path ni d'itération, aucune règle automatique.

Fiabilité

Pas de doublon, des refus explicites

tag = codeinsights-finding-{id}

WIQL : [System.Tags] CONTAINS tag

Azure DevOps ne rend pas la création idempotente. Avant de créer, le job cherche le work item portant le tag du finding et l'adopte s'il existe : une réponse perdue suivie d'une reprise ne crée pas de doublon.

Une deuxième demande sur un lien pending ou created le renvoie tel quel.

Réponses d'Azure DevOps

  • 400, 404 : terminal, message d'Azure DevOps conservé
  • 401, 403 : terminal, avec le rappel du droit Work Items (Read & Write)
  • 429, 5xx : repris jusqu'à cinq fois, puis failed
  • failed : jamais recréé par une règle, bouton Retry dans Issues

Notes de la slide 6

Rester sur les champs System.* garantit que la création fonctionne quel que soit le process du projet, pourvu que le type de work item existe. Le type est la seule chose qu'il faut adapter pour un process Basic.

Règles automatiques

Utiles sans inonder le board

Règle 1

Sévérité minimale

Nouveaux findings de cette sévérité ou plus, détectés après l'activation.

Règle 2

Dépassement de SLA

Findings breached dont l'échéance tombe après l'activation.

Plafond

auto_max_per_run

1 à 100 par projet et par passage, 10 par défaut ; le reste attend.

Branche principale, finding ouvert ou confirmé, sans lien

SLA d'abord, puis sévérités de la plus haute, plus anciens d'abord

Job sla réveillé par l'ingestion, et maintenance horaire

auto_since est fixé à l'activation et effacé quand toutes les règles sont désactivées : l'historique antérieur ne crée aucun work item.

Suite

Limites connues et prochaines étapes

Limites assumées

  • L'état du work item ne revient pas dans CodeInsights
  • Une réouverture du finding n'est pas commentée
  • Le plafond s'applique par passage, pas par analyse
  • Extensions et MCP n'affichent pas encore le lien

Prochaines étapes

  1. Commit et PR vers develop
  2. Accorder Work Items (Read & Write) à l'identité managée, puis activer la capacité
  3. Pilote : work item réel créé, adopté après reprise, commenté à la résolution
  4. Lot 3 : tendances de portefeuille
